# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Python service that turns a Jabra SPEAK 510 USB speakerphone into a voice client for the OpenClaw gateway. **Activation is selectable** (`activation` in `voice-bridge.json`): `"button"` is the flow described in this paragraph; `"wake_word"` replaces the unmute press with a spoken wake phrase (see *Wake-word activation* below). No PTT — once started, the mic stays open and an RMS-based endpointer commits each utterance after a configurable pause. **The bridge boots in mute** (LED red, USB-Audio capture firmware-silenced via output report `0x03`) and waits for the first Jabra HID button press to begin recording. A press while recording is a **soft "commit-and-mute"**: the endpointer flushes any in-progress speech buffer immediately (so the user's last utterance is still sent to STT/gateway/TTS and they hear the reply), the mic closes, and the device re-mutes — but the in-flight pipeline keeps flowing. A press while idle resumes recording. After `idle_timeout_ms` of pure silence the bridge auto-idles back to mute; if a turn was still being processed when that fires, the player un-idles itself when the reply starts so the user can talk back the moment it ends. The bridge writes the LED on every state transition, and that same write also flips the firmware capture mute — so the device's red ring and its actual mute state always agree with `recording`. It runs on a Raspberry Pi (ARM64, currently the only deployment target).

Pipeline (4 daemon threads + the HID monitor thread):

```
Recorder ──audio_q──▶ Endpointer ──utt_q──▶ Worker ──playback_q──▶ Player
```

Per utterance: PyAudio chunks flow continuously into `audio_q`; once the endpointer sees `silence_timeout_ms` of silence after speech, it pushes the buffered PCM to `utterance_q`. The worker pulls FIFO and runs STT → gateway `/v1/chat/completions` SSE → TTS streaming, pushing PCM into `playback_q`. The player owns one `aplay` subprocess per utterance. After `idle_timeout_ms` of pure silence (no speech), the bridge auto-idles: the recording stream closes and any in-flight processing is allowed to drain naturally.

Source files:
- `voice-bridge.py` — entry point + `VoiceBridge` orchestrator (worker threads, generation counter, soft auto-idle). State transitions (`_enter_idle`, `_on_hid_press`, `_resume`, `_unidle_for_reply`, …) run under one re-entrant `_state_lock` via the `@_transition` decorator, so their check-then-act on the state Events and fields is atomic across threads; a transition must never block while holding it. The helpers live in the three modules below and are re-imported by name, so `VoiceBridge` resolves them through this module (tests patch e.g. `_aplay_popen`, `play_audio`, `gateway_chat_stream_zeroclaw_ws` on it) and the old surface (`gateway_chat`, `play_audio_stream`, `play_beep`, `find_input_device`, `load_config`, …) is still importable from here.
- `bridge_config.py` — `load_config()` (reads `voice-bridge.json` + `voice-bridge.secrets.json`, `CONFIG_PATH` / `SECRETS_PATH` live here — patch them on this module) and `_build_voice_provider()`.
- `audio_io.py` — aplay plumbing (`_aplay_popen`, `_drain_aplay`, `play_audio`, `play_audio_stream`), generated tones (cached with `lru_cache`), `find_input_device`, `_apply_output_volume`, and the webrtcvad check (`_voiced_ms`, `_make_speech_vad`).
- `gateway.py` — the three gateway legs (`gateway_chat_stream`, `gateway_chat_stream_zeroclaw`, `gateway_chat_stream_zeroclaw_ws`, plus non-streaming `gateway_chat`), their fallback replies, and the turn-text helpers (`_filter_no_reply` / `_is_no_reply`, `_is_non_speech`, `_expects_answer`).
- `jabra_hid.py` — `HidMuteMonitor`: Jabra HID button watcher (background thread, edge-triggered, USB unplug-resilient). Voice-bridge only calls `start() / stop() / consume_unmute_event()` on it.
- `deepgram_voice.py` — `DeepgramVoice`: Deepgram STT (`nova-3`) + TTS (Aura). `transcribe(pcm, rate)` and `synthesize(text)`. **Deepgram TTS has no `language` param — the language is baked into the voice-model name** (`aura-2-thalia-en` English, `aura-2-livia-it` Italian, etc.; Aura-2 added Italian/French/German/Dutch/Japanese in 2025). To speak Italian, set `deepgram.ttsModel` to an `aura-2-*-it` voice; the default `aura-2-thalia-en` speaks English regardless of the input text.
- `elevenlabs_voice.py` — `ElevenLabsVoice`: ElevenLabs TTS (`eleven_multilingual_v2`, Italian) + STT (Scribe). Same `transcribe` / `synthesize` contract — providers are swappable. **TTS output format is `pcm_<tts_sample_rate>`** (raw S16LE mono at the configured rate; the class default is 22050, but `voice-bridge.json` drives it — currently 24000 → `pcm_24000`). The single `tts_sample_rate` knob feeds both the request and the `aplay` invocation, so they always match; ElevenLabs only accepts a fixed rate set (8000/16000/22050/24000/32000/44100/48000), anything else is an SDK error.
- `wake_word.py` — wake-word activation helpers: `SpeechGate` (true-RMS energy gate that cuts loud segments out of idle audio), `WakeDetector` (one-shot [Whistle](https://huggingface.co/Cactus-Compute/whistle) transcription via `cactus-needle`, forced language + keyword bias, word-boundary phrase match), `AckBank` (short clips picked at random: `acks` on a wake hit, `sleep_acks` on auto-idle; every phrase synthesized in the reply voice only — the configured `tts_provider` — so acks never sound like a different speaker; `[tone]` tags such as `[warm]` are acted by eleven_v3 and stripped for any other voice; cached as raw PCM under `~/.cache/voice-bridge/acks/<wake|sleep>/<provider>-<voice>-<model>/`, file name = hash of text + rate + language + voice settings — so changing voice, model or settings re-downloads, and clips no current voice uses are pruned at boot. A cold or partial cache is synthesized in the background, and clips that fail are retried with 30 s→10 min backoff until the set is complete — wakes meanwhile use what's ready, or a beep). Only imported for real work when `activation` is `"wake_word"`.
- `stt_compare.py` — `SttComparer`: shadow STT comparison, on with `stt_compare.enabled`. The configured remote STT stays authoritative (its text goes to the gateway); the worker then `submit()`s the same PCM + remote text, and one background thread at nice +10 runs Whistle (`stt_compare.language`, default `it`) and appends a TSV row — timestamp, audio s, provider, remote s, remote text, Whistle s, Whistle text — to `stt_compare.log_path` (default `data/stt-compare.tsv`, gitignored). `submit()` never blocks: a full queue (8 pending) drops the comparison. Shares the process's single Whistle instance with the wake loop via a lock in `wake_word.py`.
- `deezer_connect_plugin.py` — `DeezerConnectPlugin`: optional ducking integration with the deezer-connect BFF (HTTP on `localhost:8980`). Disabled-by-default; a no-op unless `deezer_connect.enabled: true` is set in `voice-bridge.json`. **Ducking tracks who is talking, not mute state:** music is ducked while the *user* speaks (the endpointer holds from the first chunk above `vad_rms_threshold` until the utterance is committed to STT — `silence_timeout_ms` pause or HID force-commit — or dropped as a too-short burst) and while the *bridge* speaks (one hold per aplay: reply, wake/sleep ack, beep, `say_to_speaker`, released after the audible tail drains). Holds overlap (talking over a reply), so `VoiceBridge` counts them (`_duck_acquire` / `_duck_release` / `_ducked()`): `duck()` on 0→1, `unduck()` on 1→0. Mute, idle, resume and processing don't touch ducking — between turns (the gateway thinking) the music is back up. `unduck()` is also called on `bridge.stop()` to recover from SIGTERM while ducked.
- `mcp_voice_server.py` — **MCP voice library** exposing the bridge's STT/TTS providers as five tools. The bridge's `main()` runs it in-process (see *MCP server* below). The import defines the `@mcp.tool()` functions and the `FastMCP` app; `configure()` loads config and providers (see there). Tools (FastMCP, streamable-http) — `speech_to_text(audio_path, mime_type?)`, `text_to_speech(text, format, out_path?)`, `send_voice_telegram(audio_path, chat_id?, caption?)`, `say_to_telegram(text, chat_id?, caption?)`, and `say_to_speaker(text)` — so an MCP *client* (e.g. zeroclaw relaying voice messages to/from a social platform) can transcribe inbound audio, synthesize spoken replies, and deliver them as native Telegram voice notes or play them aloud on the bridge's speaker. `say_to_telegram` is the **one-shot fused** path: synthesize → encode → upload → delete temp file, all in a single MCP roundtrip; the two-step variants exist for when the audio needs to be inspected or re-used. `say_to_speaker` is the **speaker-side analogue**: synthesize → hand the PCM to the running bridge's `play_pcm()`, so it behaves like a normal spoken reply. The bridge unmutes (mic open, LED off) and **ducks deezer-connect** for exactly the playback window, the audio serializes behind any reply already playing rather than overlapping it (enqueued as one atomic `_ExternalUtterance` on `playback_q`), and after the speech the usual `idle_timeout_ms` timer re-mutes — the same tail as a real reply. It blocks until playback finishes (returns `{ok, chars, seconds}`). The text decides the tail (`_after_external`): an announcement that expects an answer gets `idle_after_question_ms` and counts as a conversation (goodbye later); a plain one keeps `idle_timeout_ms` and, unless a conversation was already going, dozes off with no goodbye and no tone (`_quiet_idle`). It needs `aplay` on PATH and `audio`-group access (the bridge unit already inherits that group). The Telegram delivery tools POST `sendVoice` directly to `api.telegram.org` with the bot token from `voice-bridge.secrets.json` → `telegram_bot_token`; it does NOT poll `getUpdates`, so it coexists with any other process (e.g. zeroclaw's Telegram channel) that *is* long-polling the same bot. `chat_id` defaults to `telegram.chat_id` from `voice-bridge.json` (the bridge's bound recipient) and is overridable per-call.

  **MCP server.** The module is a library with two entry points: `configure(cfg, *, stt, tts, bridge)` resolves the injected config + provider instances into module globals, and `serve_background()` runs uvicorn in a daemon thread with its signal handlers disabled (the bridge owns SIGTERM/SIGINT). The bridge's `main()` calls both when `mcp_server.enabled: true`, so **one process, one systemd unit, one config load, and the SAME provider instances** serve both the voice client and the MCP tools. The injected `bridge` is the running `VoiceBridge`, whose `play_pcm()` lets `say_to_speaker` speak through the bridge's player (unmute → duck → idle re-mute, like a real reply); providers are shared safely (`ElevenLabsVoice` reuses one thread-safe SDK client, so its HTTPS connection stays warm between calls; `DeepgramVoice` builds one per call). Best-effort: if the server fails to start, it's logged and the always-on voice client keeps running. All container handling (ogg/opus, mp3, wav) is delegated to `ffmpeg` at the tool boundary so the providers stay PCM-centric — see *Architecture notes*.
- `tests/test_hid_mute.py` — automated unit tests for the HID monitor (uses `os.pipe()` as a fake `/dev/hidraw`, no Jabra needed).
- `tests/test_hid_interactive.py` — interactive smoke test against the real Jabra (run on the Pi with the device plugged in).
- `tests/test_voice_providers.py` — interface/contract tests for the two voice providers (verifies same surface, safe fallbacks on bad input, defaults pinned).
- `tests/test_gateway_integration.py` — end-to-end gateway leg: drives `load_config()` + `gateway_chat()` against the live gateway, skips when unreachable.

## Run / develop

```bash
# Activate the local venv (Python 3.13, ARM-aarch64 wheels) and run directly:
.venv/bin/python voice-bridge.py
```

`.venv/` is gitignored (too large at ~68 MB). To bring it up on a fresh checkout:

```bash
python3 -m venv .venv
.venv/bin/pip install -r requirements.txt
```

There's no global Python tooling for `deepgram`, `elevenlabs`, `pyaudio` on the host Pi, so always install into the local `.venv`, never `pip install --user`.

## Config — self-contained in this folder

The bridge is **self-contained**: everything it needs lives in this directory. `load_config()` reads two local files and edits take effect on `systemctl --user restart voice-bridge`:

1. `voice-bridge.json` (tracked, **no secrets**): all non-secret config.
   - **Audio I/O**: `sample_rate` (mic), `chunk_size` (PyAudio frames per read), `tts_sample_rate` (TTS output + `aplay` rate — MUST match), `output_device` (ALSA PCM name).
   - **Endpointer / VAD**: `vad_rms_threshold` (per-chunk energy above which a chunk counts as speech; same `sum(s²)/sqrt(N)` metric the legacy code used, NOT true RMS — see *Architecture notes*), `silence_timeout_ms` (pause after speech that commits an utterance; values <600 ms split natural between-word pauses), `min_speech_ms` (minimum above-threshold audio for an utterance to reach STT — shorter bursts such as key clicks or speaker-echo blips are dropped before STT and don't reset the idle timer; default 0 = off, deployed 200 ms. Calibration note: with `chunk_size` 1024, `vad_rms_threshold` = 32 × true-RMS²; the Jabra's room floor is true RMS ~160–210 (≈0.8e6–1.4e6), noise bursts crossed at 1.8e6–3.3e6 for only 1–2 chunks, speech onsets are mostly ≥2e7 — hence 6e6 (true RMS ~430, ~2× over the loudest noise bursts and ~3× under typical voice onsets; was 1e7 until 2026-10) + 200 ms + `pre_speech_keep_ms` 250 to keep word onsets), `idle_timeout_ms` (cumulative silence after which the mic stream is closed; set to `0` to disable auto-idle), `idle_after_reply_ms` / `idle_after_question_ms` (the idle window right after a reply finished playing, and after one that ended with "?"; both default to `idle_timeout_ms`, deployed 8000 / 12000 so the user has time to answer; a reply "expects an answer" when its last two sentences contain a `?` or the last one is an invitation such as "dimmi", "rifammi" — `_expects_answer`), `idle_after_resume_ms` (the window right after a wake word / button resume, time to start talking after "Dimmi"; defaults to `idle_timeout_ms`, deployed 6000; a commit resets the window to `idle_timeout_ms`), `max_utterance_ms` (an utterance still going after this long is people talking among themselves — seen: 19–34 s of family chat sent as one turn — so it is dropped before STT and the bridge goes idle; default 0 = off, deployed 18000, the longest real request seen was ~11 s), `speech_filter` (`enabled`, `aggressiveness` 0–3, `min_voiced_ms`: at commit, webrtcvad counts voiced 30 ms frames and an utterance below `min_voiced_ms` is dropped before STT like a burst — keyboard, TV, doors; every commit logs `N ms voiced` so the threshold can be tuned from the journal; HID force-commits skip it; needs `webrtcvad-wheels`, a missing module only disables the filter).
   - **Playback / feedback**: `playback_prebuffer_ms` (PCM collected before the first aplay write, default 0, deployed 500: ElevenLabs v3 sends one chunk then stalls ~0.5 s, which underran aplay on most replies; capped at prebuffer + 1 s so a slow stream still starts), `thinking_cue` (`enabled`, `delay_ms`, `repeat_ms`, `phrases`: dead-air feedback between pick-up and the first reply audio — a soft tick after `delay_ms` repeated every `repeat_ms`, and one random spoken phrase on the first `tool_call` frame of the `zeroclaw_ws` leg; cues go through the player queue without ducking, never land behind the reply, and phrases are cached like acks under `acks/thinking/`).
   - **Control**: `activation` (`button` default, or `wake_word` — see *Architecture notes*), `hid_mute_enabled` (whether the Jabra HID button toggles the bridge), `stt_provider` / `tts_provider` (`elevenlabs` or `deepgram`), `tts_streaming_mode`, `tts_whole_reply` and `tts_first_sentence_early` (see *Architecture notes*), `gateway_backend` (`openclaw` (default), `zeroclaw`, or `zeroclaw_ws`; see *Architecture notes*), `gateway_agent` (agent alias for the `zeroclaw_ws` WebSocket leg; default `"default"`), `session_key` (sent verbatim as `X-OpenClaw-Session-Key`; OpenClaw backend only — see session-key note below), `voice_model` (gateway agent/model; defaults to `"openclaw"` → gateway's default agent, currently `main`; OpenClaw backend only), `gateway_base_url`.
   - **`elevenlabs` block** (non-secret TTS settings): `voiceId`, `modelId` (note camelCase — `modelId`, not `model`), `languageCode`, `applyTextNormalization`, `voiceSettings`. The `voiceSettings` keys are converted from camelCase (`similarityBoost`, `useSpeakerBoost`) to the SDK's snake_case (`similarity_boost`, `use_speaker_boost`) at load-config time. The bridge does not fabricate these — whatever's here is what's used.
   - **`deepgram` block**: `sttModel` (e.g. `nova-3`), `ttsModel` (Aura voice model, e.g. `aura-2-livia-it` for Italian — language is implied by the voice, see *Source files*; defaults to `aura-2-thalia-en`/English if unset), and `sttOptions` (extra STT kwargs like `smart_format`, `punctuate`, `detect_language`, passed verbatim — already snake_case). Only used if a Deepgram provider is selected.
2. `voice-bridge.secrets.json` (**gitignored**, secrets only): `gateway_token` (bearer for `/v1/chat/completions`), `elevenlabs_api_key`, `deepgram_api_key`, optional `telegram_bot_token` (consumed only by the MCP sidecar's `send_voice_telegram` tool; ignored by the bridge itself). Copy `resources/voice-bridge.secrets.example.json` → `voice-bridge.secrets.json` and fill in on a fresh checkout. `DEEPGRAM_API_KEY` env var, if set, overrides `deepgram_api_key`.

The optional **`mcp_server` block** in `voice-bridge.json` configures the embedded MCP voice server: `enabled` (default `false`) is the on/off switch, plus `host` (default `127.0.0.1`), `port` (default `9080`), and `out_dir` (where synthesized files are written; default `<tmp>/voice-bridge-mcp`). When `enabled: true` the **bridge process** starts the MCP server in a background thread (one unit, shared providers — see the `mcp_voice_server.py` entry under *Source files*).

To switch which voice provider is used, or to change any voice/agent behavior, edit `voice-bridge.json` (secrets go in `voice-bridge.secrets.json`). Never commit real keys — they belong only in the gitignored secrets file. `load_config()` reads **only** these two local files; the bridge has no dependency on the wider OpenClaw gateway config.

> **Don't move `voice_model` / `session_key` into the gateway config.** These live in `voice-bridge.json`. The gateway's config schema **rejects** `agents.defaults.voiceBridgeModel` and a top-level `voice.sessionKey` block — adding them makes the gateway hard-crash at startup (`Unrecognized key: ...`; at runtime it merely "skips reload", masking the bomb until the next restart). `voice_model` defaults to `"openclaw"` → the gateway's default agent (currently `main`).

## Architecture notes that aren't obvious from one file

- **Wake-word activation** (`"activation": "wake_word"`, tuned in the `wake_word` block). Three states instead of two: *recording*; *idle-but-listening* (`_wake_armed` set — the recorder keeps the mic open and routes chunks to `wake_q`, and `_wake_loop` gates them with `SpeechGate` and runs Whistle only on segments that crossed `rms_threshold` for at least `min_loud_ms`); and *privacy-muted* (HID press while recording — firmware-muted, LED red, wake word off, only the button resumes). Boot and auto-idle land in idle-but-listening, which **must leave the firmware mic unmuted** (the LED mute bit is also the capture mute), so the LED is off while idle; red now means "privacy mute". Auto-idle says a random `sleep_acks` goodbye unless a turn is in flight — `_worker_busy` (set from pick-up until the worker loops back), queued utterances, or a reply queued/playing — since the player will un-idle for that reply. The wake loop ignores the mic while any clip plays (`_speaking_ack`). A hit runs the same `_resume()` as an HID press **first**, then plays a random cached ack in a background thread (beep if none are ready yet; skipped if a reply is already playing) — the mic is open while the ack plays, so "Hey Binary… metti la musica" said in one breath isn't cut. The audio queued in `wake_q` while Whistle transcribed is handed to the endpointer (`_resume(prefill=…)`, re-chunked to `chunk_size` because the VAD metric depends on N); when Whistle heard words after the phrase (`wake_word.command_after`), the wake segment itself goes too, so STT gets the whole sentence, and a soft tick replaces the spoken ack so it doesn't talk over the user. Measured on the Pi 3B+: Whistle loads in ~3 s and ~75 MB, a 1–2 s segment transcribes in ~0.4 s, idle CPU ~3–6% — continuous streaming instead cost ~230% and fell behind. Two things learned the hard way: Whistle hallucinates "Thank you." / "Vielen Dank." on non-speech (hence the gate), and with auto-detect it heard "Hey, Binary" as Spanish — `language` forced + the phrases as keyword bias caught every take. Matching is also fuzzy: `wake_word.fuzzy_threshold` (default 0.8, `0` = exact only) accepts a window of heard words whose letters (spaces removed, difflib ratio) are that close to a phrase — "hey binally", "okay binary" — while "hey baby"/"hey bud" stay out; `wake_word.aliases` are extra exact phrases (observed mishearings such as "hey bye harry") that are deliberately NOT passed to Whistle as keyword bias. `wake_word.goodbye_after_turn_only` (default true): a `sleep_acks` goodbye is spoken only if a reply was played since the last wake/resume; an unanswered wake dozes off with a soft two-note tone. The wake word is `wake_word.phrases` (one or more; matched case/punctuation-insensitively on word boundaries, and passed to Whistle as keyword bias) and `wake_word.language` is the language Whistle decodes it in — one of `en de fr es it nl pl`, or `null` to auto-detect (not recommended, see above). Both are validated in `load_config()`. `rms_threshold` is **true RMS**, unlike `vad_rms_threshold`. `cactus-needle` telemetry is disabled (`NEEDLE_TELEMETRY=0`) before import.

- **Always-on mic, four async stages.** `VoiceBridge` runs five daemon threads (HID poller + recorder + endpointer + worker + player) connected by `queue.Queue` instances. The recorder keeps PyAudio open while `recording.is_set()`; the endpointer commits utterances on `silence_timeout_ms` pauses; the worker drives the streaming STT/gateway/TTS pipeline; the player owns one `aplay` per utterance. CPU is low (recorder blocks in `stream.read`, endpointer is `O(chunk_size)` per ~64 ms frame) but no longer ~0% the way the old wake-on-press model was — that's an intentional trade for sub-second time-to-speak.
- **HID press while a reply plays = stop it and listen** (`_stop_reply`). If the player has an aplay open or anything queued, a press (recording or muted) runs `_resume()` (gen bump, mic open, LED off), drains `playback_q`/`utterance_q` (releasing any blocked `say_to_speaker` caller) and kills aplay. A press during *processing* is still the privacy mute below, and a press with nothing playing keeps the soft rules.
- **No hard cancel — every other "stop" is soft.** HID press while recording sets `_force_commit` (the endpointer flushes any in-progress speech buffer at the next loop tick, instead of waiting for `silence_timeout_ms`) and clears `recording`. Queues are NOT drained, `_gen` is NOT bumped, the active aplay is NOT killed — the worker still picks the committed utterance off `utterance_q`, the player still plays the reply, the user just stops being listened to until the next press. Auto-idle (silence ≥ `idle_timeout_ms`) does the same thing minus the force-commit: clears `recording`, drains `audio_q` (the chunks the recorder pushed during the silence window are no longer interesting), sets `_auto_idled`. Resuming via HID press bumps `_gen` (sheds any half-built endpointer state under the old gen) and clears `_auto_idled`.
- **At most ONE message waits behind the turn in flight** (`_enqueue_utterance` + the worker's wait loop). The worker handles one turn at a time and the gateway can take many seconds, while the endpointer keeps committing whatever it hears (follow-ups, side talk, speaker echo). Earlier the whole backlog was merged into one turn, which produced muddled 10 s transcripts; now, while `_worker_busy` is set, the endpointer enqueues only if `utterance_q` is empty and drops later commits, and a picked-up utterance waits until the previous reply has finished playing (`playback_q` non-empty *or* `_is_playing()`), discarding anything else queued meanwhile (stale-gen items are dropped too). First wins: the first thing said during a busy turn is the next turn. Well-behaved turn-taking pays no latency: with nothing in flight the wait loop never runs.
- **The mic is paused while the agent processes** (`_processing`, `_pause_for_processing`). Every normal commit that reaches `utterance_q` clears `recording` (and drains `audio_q`) without touching the LED/firmware mute, and sets `_auto_idled`, so the player's existing auto-resume reopens the mic when the reply's first PCM arrives. If the turn ends with nothing to play (non-speech, empty STT, gateway error), the worker's loop head calls `_resume_after_processing()` once queues are empty. The wake word is off during the pause (`_wake_armed` clear) and idle/goodbye can't fire (recording is already clear). An HID press during the pause is a privacy mute *without* a gen bump, so the reply still plays and the mic stays muted afterwards. Net effect: only speech said during playback can become the one queued message.
- **Auto-resume on playback** (`_auto_idled` flag). If the bridge auto-idled while a turn was still being processed, the player un-idles itself when the first PCM chunk arrives — sets `recording`, writes `set_led(muted=False)`, resets `silence_count` via `_idle_reset_pending`, and clears `_auto_idled`. No `_gen` bump (we're inside the same turn). The user can talk back the instant the reply ends instead of having to press HID first. Crucially, this only fires on *auto*-idle: if the user explicitly pressed HID to mute, `_auto_idled` is clear and the player respects the press — playback happens but the mic stays muted afterwards.
- **VAD metric is `sum(s²) / sqrt(N)`, NOT true RMS.** The legacy `record_until_silence` had operator-precedence accidents (`/ len(samples) ** 0.5` evaluates `**` first), and the threshold defaults were calibrated against this dimensionally-weird quantity. The new endpointer keeps the same formula on purpose so prior tunings of `vad_rms_threshold` carry over. If you ever fix it to true RMS, also re-tune the default by ~`sqrt(chunk_size)`.
- **HID monitor lives in `jabra_hid.py`** as `HidMuteMonitor`, runs in a daemon thread (`_poll_loop`) reading raw reports from `/dev/hidraw*`. Device discovery matches USB vendor `0B0E` / product `0422` via `/sys/class/hidraw/*/device/uevent`. Open is `O_RDWR` — required for the engage write. The poll loop owns the device lifecycle: if the Jabra is absent at startup or disappears mid-run, it parks in `_shutdown.wait(2.0)` (Event-based, kernel-blocked, ~0 CPU) and retries `_open_device()` every 2 s until it appears or `stop()` is called. `start()` no longer returns a success bool — there is no "device absent at startup" failure path; plug state is runtime state.
- **The Jabra needs an off-hook engage write** (`bytes([0x03, 0x01, 0x00])` = output report `0x03` with LED Off-Hook bit set) before it emits any telephony input reports. Without it, pressing mute is silent on every interface — hidraw, `/dev/input/event*`, ALSA. `start()` writes this once. Full protocol details and the diagnostic trail are in `docs/JABRA.md`.
- **Bit 4 of byte 1 of report `0x03` is the *Mic Mute button-press* state** (momentary: high while held, low when released), HID Telephony usage `0x2F`. A single press emits a 1→0 sequence; the monitor edge-triggers on the rising edge so each press = exactly one wake event. The bit is marked `Constant` in the descriptor, which is why the kernel input layer doesn't surface it as `KEY_MICMUTE`.
- **Set `JABRA_HID_DEBUG=1`** to log every incoming HID report's first 8 bytes in hex — useful when diagnosing a different device variant or unexpected report layout.
- **Set `VOICE_BRIDGE_DEBUG_AUDIO=1`** to surface aplay's stderr (drops `-q`, forwards lines to the Python logger via a daemon thread). Use it to spot `underrun!!!` lines when the streaming TTS pipeline can't keep aplay's ALSA buffer fed — otherwise underruns are silent except for an audible click.
- **Host-driven mute, not host-tracked.** The bridge is the source of truth for mute state. `HidMuteMonitor` exposes `consume_unmute_event()` (edge-triggered "user pressed") *and* `set_led(muted: bool)`, which writes output report `0x03` with the Off-Hook + Mute bits. **The Mute bit is also the firmware capture-mute switch on this device** (verified by PCM probe: 0/14400 vs ~14400/14400 non-zero samples per second), so a single write controls both the red LED ring and whether the USB-Audio endpoint emits silence. `VoiceBridge` keeps the `recording` Event and calls `set_led(muted=not recording.is_set())` on every transition (HID press, auto-idle), so the device's actual mute always matches the bridge's intent. The boot default is muted (`_muted_pref=True` in `HidMuteMonitor`); `_engage()` re-applies the preference on every reconnect, so an unplug/replug snaps the device back to whatever the bridge currently wants instead of resetting.
- **Session-key handling.** The bridge sends `X-OpenClaw-Session-Key: <value>` per turn. The gateway's `resolveSessionKey` accepts the header **verbatim** — it does NOT add the canonical `agent:<agentId>:` prefix. Anything that isn't already in `agent:<id>:<rest>` shape becomes an "orphaned" session that the UI hides until the gateway's next-boot migration canonicalizes it (one-shot, not per-request, and a no-op once the canonical key already exists). The pinned value `agent:main:voice-bridge` in `voice-bridge.json` keeps every turn flowing into the same canonical session under the `main` agent (the existing on-disk session is `agents/main/sessions/<sessionId>.jsonl` keyed `agent:main:voice-bridge`). Don't change to a non-canonical key unless you understand this.
- **Tests:**
  - `.venv/bin/python tests/test_hid_mute.py` — automated, no hardware required. Drives `HidMuteMonitor` over an `os.pipe()` and asserts the edge-detection logic.
  - `.venv/bin/python tests/test_hid_interactive.py [N]` — manual hands-on test on the Pi: prompts the operator to press the button N times (default 3) and checks that exactly N wake events fire with reasonable spacing and no spurious extras. Use this when porting to a different host, after udev/permissions changes, or to confirm a wire-protocol fix on real hardware.
  - `.venv/bin/python tests/test_voice_providers.py` — provider interface/contract tests, no network.
  - `.venv/bin/python tests/test_gateway_integration.py` — gateway leg integration test; auto-skips if the gateway isn't reachable.
- **deezer-connect ducking (`deezer_connect` block in `voice-bridge.json`).** When `enabled: true`, when someone starts talking (user speech onset or bridge playback) it asks the deezer-connect BFF for its current volume via `GET /api/player/status`, multiplies it by `ducking_percent/100` (default 50), and writes the result back via `POST /api/player/volume`; when nobody is talking any more (utterance committed to STT and no playback) it **restores the volume it read *before* ducking** (the pre-duck level is remembered in `_original_volume`, not assumed). See the `deezer_connect_plugin.py` entry under *Source files* for the exact hold points. Failures (BFF down, timeout, malformed JSON) are logged and swallowed — voice-bridge keeps playing the reply, just without the side-effect. The plugin is **off by default**: missing block or `enabled: false` makes `DeezerConnectPlugin.duck/unduck/apply_default_volume` no-ops, so it's free to leave the code path wired in. `default_volume_percent` (default 75) is a **startup baseline**: when enabled, `bridge.start()` calls `apply_default_volume()` once to pin the player to that level — it does *not* change ducking, which always reads-then-restores the live pre-duck volume. `request_timeout_s` (default 1.0) caps how long the player will wait on the BFF before giving up — keep it tight, since this call sits on the critical path before aplay opens (and in the endpointer at speech onset).
- **TTS streaming strategy (`tts_streaming_mode` in `voice-bridge.json`).** Default `"http_sentence"`: gateway deltas are buffered to a sentence boundary (`[.!?…]` + whitespace), then `text_to_speech.stream()` (HTTP) is called once per sentence and its PCM chunks are forwarded to `aplay`. Available on every ElevenLabs tier; first-audio latency ≈ first sentence. Alternative `"websocket"`: feeds deltas straight into `text_to_speech.convert_realtime` for token-level latency, but **requires a paid ElevenLabs tier** — free accounts get HTTP 403 on the WS upgrade. Only consulted when `tts_provider == "elevenlabs"`. The `language_code` and `apply_text_normalization` settings are forwarded only on the HTTP path; the WS endpoint rejects them, so don't rely on either when running in `websocket` mode.
- **Whole-reply TTS (`tts_whole_reply` in `voice-bridge.json`, default `false`).** When `true`, the HTTP path stops splitting per sentence: all gateway deltas are buffered until the stream ends and synthesized in ONE `text_to_speech.stream()` call (`_synthesize_stream_http_whole`). The point is **tone consistency**: with per-sentence calls each sentence is an independent generation with no context, so tone/energy drifts between them. ElevenLabs' fix for that, request stitching (`previous_request_ids` / `previous_text`), is **rejected by `eleven_v3`** with 400 `unsupported_model` (both variants; verified 2026-09), so on v3 this flag is the only consistency lever. Cost: first-audio latency becomes gateway-complete + TTS-first-byte (measured ≈0.9 s TTS first byte on v3 after the gateway finishes) instead of first-sentence. PCM is still forwarded to `aplay` as it arrives, so it's the LLM tail we wait for, not TTS. Ignored on the `websocket` path (one generation context per reply already) and by Deepgram (its `synthesize_stream` already buffers whole). **`tts_first_sentence_early: true`** (with `tts_whole_reply`) is the hybrid: the first sentence is synthesized the moment it is complete — so the agent's "ci penso io" is heard while it keeps working — and everything after it in one more call. One tone seam instead of one per sentence. A sentence boundary only counts once the text before it has a word in it (`_sentence_end`): the agent opens every reply with `... `, which the bare regex took as the whole first sentence — a TTS call for three dots, the real first sentence then waiting for the whole reply.
- **Turn timing.** Every turn logs `Turn timing (s from pick-up): stt=… first_token=… gateway_done=… first_pcm=…, cues=N`, and the player logs `Turn: first audio X s after pick-up` — the place to look when replies feel slow.
- **Italian is hardcoded** in `transcribe_audio` (`language="it"`) and the fallback error string. If multilingual support is needed, plumb it through config.
- **Gateway backend (`gateway_backend` in `voice-bridge.json`).** Selects which gateway protocol the worker speaks; they are NOT wire-compatible, and `gateway_base_url` / `gateway_token` must point at the matching server.
  - `"openclaw"` (default): posts `POST /v1/chat/completions` with `stream: true` and parses OpenAI-style SSE (`gateway_chat_stream`). Uses `voice_model` and the `X-OpenClaw-Session-Key` header (`session_key`).
  - `"zeroclaw"`: posts `POST /webhook` with `{"message": "..."}` and parses a single non-streaming JSON `{"response": "..."}` reply (`gateway_chat_stream_zeroclaw`). There is no SSE and no session header — **conversational context is keyed by the bearer token itself** (the token *is* the session), so `voice_model` and `session_key` are ignored. The token is a `zc_`-prefixed *paired token*: it is not stored in clear anywhere on the zeroclaw side (config holds only `enc2:` hashes in `[gateway].paired_tokens`); mint one with `zeroclaw gateway get-paircode --new`, then `POST /pair` with header `X-Pairing-Code: <code>` to receive the `zc_...` token, and put it in `voice-bridge.secrets.json` → `gateway_token`. The whole reply is yielded as one delta; the downstream sentence buffer still splits it for `http_sentence` TTS. **Caveat — reasoning leaks into TTS:** the webhook is non-streaming, so zeroclaw returns the tool loop's whole `accumulated_display_text`; on a reasoning model (e.g. `deepseek-reasoner`) the intermediate tool-step narration *is* the chain-of-thought and gets concatenated in front of the answer with no delimiter, so TTS reads it aloud. Use `"zeroclaw_ws"` instead to avoid this.
  - **WS failures:** if the message never left (connect/upgrade failed) the leg retries once, then speaks `GATEWAY_UNREACHABLE_REPLY`; if it was sent but no answer text arrived it speaks `GATEWAY_LOST_REPLY` and does NOT retry (the agent may already have acted — a retry would act twice); after partial answer text it stops quietly. Non-chunk frames are reported to an `on_event` callback (the thinking cue listens for `tool_call`). The agent opens every spoken reply with `... `, so the `NO_REPLY` filter strips leading dots before comparing.
  - `"zeroclaw_ws"` (preferred for zeroclaw): streams over the `GET /ws/chat?agent=<gateway_agent>&session_id=<session_key>&token=<token>` WebSocket (`gateway_chat_stream_zeroclaw_ws`, via `websockets.sync.client`). Sends `{"type":"message","content":...}` and yields **only `{"type":"chunk"}` frames** — the answer. zeroclaw streams reasoning as separate `{"type":"thinking"}` frames and tool activity as `tool_call`/`tool_result`, all of which are **dropped**, so deepseek-reasoner's chain-of-thought never reaches TTS (the lossy `done.full_response` is also ignored). `approval_request` frames are auto-**denied** (voice has no interactive approval path). Same `zc_...` paired token as `"zeroclaw"`; needs an explicit `gateway_agent` (zeroclaw requires `?agent=`, runtime synthesizes a `default` even when `[agents]` is empty). Context is keyed by `session_id` (gateway namespaces it `gw_<id>`), so `session_key` doubles as the WS session id here; `voice_model` is unused.
- **TTS / gateway calls use `urllib.request`**, not `httpx`/the SDKs — keeps dependency surface minimal on ARM. Deepgram is the only one using its async SDK.
- **Output device** is an ALSA PCM name (the bridge points `output_device` at `voice_out`, defined in `~/.asoundrc` — install from `resources/asoundrc.example`), not a card index. `aplay` is invoked as a subprocess with `S16_LE mono @ tts_sample_rate` (currently 24000 Hz). That rate is the single knob: both providers emit at it (`pcm_<rate>` for ElevenLabs, `sample_rate=<rate>` for Deepgram), so changing `tts_sample_rate` moves the TTS request and the `aplay` rate together — never set one without the other. `~/.asoundrc`'s `voice_out` plug resamples this up to `sw_dmix`'s 48 kHz slave.
- **`find_input_device`** matches "jabra" case-insensitively in PyAudio's device list; there is no equivalent fallback for output (output goes through ALSA by name).
- **MCP voice sidecar (`mcp_voice_server.py`) routes ALL container conversion through `ffmpeg`, deliberately.** The providers only speak S16LE PCM (that's what `aplay` needs). Rather than asking ElevenLabs/Deepgram to emit mp3/ogg directly — which is tier- and provider-dependent (e.g. ElevenLabs OGG/Opus isn't on every plan) — the server keeps one uniform path: STT decodes whatever arrives to PCM (`ffmpeg -i <file> -f s16le -ar 16000 -ac 1`) before `transcribe()`, and TTS pipes `synthesize()`'s PCM into `ffmpeg` to build the requested container (`libmp3lame` for mp3, `libopus`-in-Ogg for ogg, raw for wav). So the only host dependency the sidecar adds is `ffmpeg` built with libmp3lame + libopus. Tools take/return **file paths** (the client shares the Pi's filesystem and owns cleanup), not inline base64. `_STT_RATE` (16 kHz decode target) and `_OUTPUT_FORMATS` (the encoder/MIME table) are the two knobs; the providers themselves are untouched.
- **Telegram voice delivery (`send_voice_telegram` / `say_to_telegram`) is a one-shot Bot API POST, not a long-poll.** Both tools read the bot token from `voice-bridge.secrets.json` → `telegram_bot_token` and POST `multipart/form-data` to `https://api.telegram.org/bot<token>/sendVoice` via `urllib.request` (consistent with the rest of the codebase's "no extra HTTP deps on ARM" rule). Neither tool calls `getUpdates`, so they do NOT trigger Telegram's 409 conflict against another process that *is* long-polling the same bot — typical setup is zeroclaw's Telegram channel polling for inbound messages while these tools fire outbound voice notes. `say_to_telegram` is the fused fast-path that callers should prefer: it synthesizes, encodes, uploads, and unlinks the temp file in a single MCP roundtrip, so no path leaks to the client and the OGG never lingers in `_OUT_DIR`. The bot token has to be present in cleartext in the secrets file (Telegram has no scoped/short-lived tokens), which is the explicit tradeoff for keeping the delivery path local; rotate via BotFather if it leaks. `chat_id` is resolved per call by `_resolve_chat_id`: explicit parameter > `voice-bridge.json` → `telegram.chat_id`; the helper raises if both are empty so a misconfigured deployment fails loud at the first call rather than silently sending to nobody. The file is uploaded as `voice` (Opus-in-Ogg) so Telegram renders the native voice-note UI (waveform + speed control) rather than a generic audio attachment.

## Deployment context

Run as a long-lived **user** systemd process on the Pi. `SIGTERM`/`SIGINT` are handled — it finishes any in-flight turn, stops the HID thread, and exits cleanly. Don't add a PID file or daemonization here; that's the unit's job.

`systemd/voice-bridge.service` is a user unit (linked into `~/.config/systemd/user/`, no `User=` directive). It runs as the invoking user (`openclaw`) and inherits that user's groups; `audio` is needed for ALSA, `plugdev` for /dev/hidraw* (granted by the udev rule). Linger (`loginctl enable-linger`) makes the user-mode systemd start at boot without a login session.

`systemd/99-voice-bridge.rules` (udev) sets `GROUP=plugdev MODE=0660` on the Jabra's hidraw node so the user can open it. The rule does **not** trigger the service — the bridge's reconnect loop handles plug/unplug on its own (`_poll_loop` parks on `_shutdown.wait(2.0)` between `_find_device()` attempts). This decoupling is what enabled moving from system to user systemd: udev can't directly start user units.

`systemd/install.sh` does the link + reload + linger + group sanity checks; see `systemd/README.md` for details. Most operations on the user unit don't need sudo at all.

`voice-bridge.service` is the single unit for both the voice client and the MCP tools: the MCP voice server runs inside the bridge process when `mcp_server.enabled: true` (see *Config* and the `mcp_voice_server.py` entry), so restart this unit to pick up any MCP change. It needs `ffmpeg` on PATH (for the MCP tools' container conversion) in addition to its existing `audio`/`plugdev` access.
